# 渐进式兼容加固设计

更新日期：2026-07-29

## 目标

在不改变现有命令、公开 Python 导入路径和生产运行入口的前提下，分阶段完成以下改进：

1. 客户台账快照原子、幂等发布。
2. 工单、客户、联系人和台账导入失败原因结构化。
3. 工单 API 对瞬时网络和服务端故障进行受控重试。
4. 用显式、版本化迁移替代运行时隐式修改生产表。
5. 通过兼容层渐进拆分超大模块。
6. 增加 Ruff、格式检查和覆盖率质量门禁。
7. 修正 CLI 默认值、帮助文本和带日期本地文件默认值。

本设计采用渐进式兼容重构。每一阶段必须独立测试、独立审查并形成窄提交；不得一次性重写数据导入或 CLI 架构。

## 边界

- 保留 `work_order_process.mysql_storage` 的现有公开函数、DDL 常量和类型导出。
- 保留 `work_order_process.api.WorkOrderClient` 的构造方式和公开方法。
- 保留 `uv run work_order_process ...`、`uv run erp-merge ...` 和
  `python -m work_order_process.daily_runner` 入口。
- 不连接或修改真实生产数据库，不部署服务器，不执行生产迁移。
- 不扫描、修改或提交 `data/` 及当前工作树中的其他用户未跟踪文件。
- 不对 `customer_account` 擅自增加业务唯一约束。
- 不在失败摘要中保存密码、完整请求体或敏感联系人字段。
- 所有行为修改先写能正确失败的测试，再写最小实现。

## 方案选择

### 采用方案：渐进式兼容重构

先修数据正确性和错误可解释性，再引入迁移、HTTP 重试和模块边界，最后增加质量门禁。旧模块通过重新导出或薄包装继续提供兼容接口。

### 未采用方案：一次性重写

一次性拆分 `mysql_storage.py`、`api.py` 和 CLI 会同时改变导入、解析、数据库和命令分发边界，回归面过大，不适合已有生产数据的项目。

### 未采用方案：只修正确性问题

仅修客户台账和失败报告无法完成版本化迁移、长期模块维护和 CI 质量门禁目标。

## 客户台账原子快照

### 数据流

```text
Excel 流式读取
  -> 严格字段转换与业务清洗
  -> 临时表分批写入
  -> 快照级校验
  -> 单事务删除同日期旧快照
  -> 从临时表发布
  -> 正式表行数校验
  -> 提交
```

### 解析与清洗

- 空金额和空日期继续转换为 `NULL`。
- 非空金额、日期或整数无法解析时生成结构化失败，并终止整个快照发布。
- “合同签约客户”和“最终使用客户”同时为空的行属于明确业务清洗，计入
  `cleaned`，不计入 `failed`。
- 不根据合同编码、标的行编码或客户字段对源文件行去重；业务重复行原样保留。
- 接受行数等于源数据行数减去表头和业务清洗行数。

### 发布事务

- 临时表结构从 `customer_account` 正式表复制，不改变正式表。
- 临时表全部写入并校验后才开始发布事务。
- 发布事务固定执行：

```sql
DELETE FROM customer_account WHERE create_date = %s;
INSERT INTO customer_account (<columns>)
SELECT <columns> FROM customer_account_import_stage WHERE create_date = %s;
SELECT COUNT(*) FROM customer_account WHERE create_date = %s;
```

- 正式表计数必须等于临时表接受行数，否则抛出快照发布异常并回滚。
- 同一 `create_date` 重跑时完整替换旧快照，结果与单次执行一致。
- 解析、临时表写入、校验和发布任一步骤失败时，旧正式快照保持不变。

## 统一失败模型

新增不可变失败记录，至少包含：

```text
stage
record_id
source_row
error_type
safe_message
```

其中 `record_id` 和 `source_row` 均可为空，但每条失败至少提供其中一个。

### 分类规则

- `skipped` 仅表示目标记录已经是最新版本或同一同步批次内明确按稳定 ID 去重。
- 明确业务清洗使用单独的 `cleaned` 计数。
- 解析异常、API 异常和数据库异常全部计入 `failed`。
- 工单导入不再只保存 `failed_ids`；保留该字段用于兼容，同时新增失败摘要。
- 客户和联系人批量写入失败后允许逐行回退，但批次异常和最终失败行都必须可追溯。

### 保存边界

- 报告包含失败总数和最多 100 条失败摘要。
- `sync_task_log.extra_json` 保存安全摘要、批次上下文和截断标记。
- 客户及联系人原始记录继续通过 `api_raw_record` 和 `batch_id` 关联。
- `safe_message` 只包含异常类型、业务阶段和非敏感标识，不包含凭据、完整载荷、电话号码或邮箱。

## HTTP 瞬时重试

HTTP 传输行为从 `WorkOrderClient` 中抽取到独立、可测试的传输模块，公开客户端接口保持不变。

### 重试条件

- 重试 `httpx.TransportError` 等网络传输异常。
- 重试 HTTP `429`、`502`、`503` 和 `504`。
- 不重试 `401`、`403`、`404` 和其他普通 4xx。
- 默认总尝试次数保持为 3 次。

### 等待策略

- 响应包含有效 `Retry-After` 秒数时优先使用该值。
- 否则使用有上限的指数退避和随机抖动。
- 测试通过注入等待函数和随机函数避免真实休眠。
- 最终失败保留最后一次状态码或异常类型，并转换为现有调用方可处理的错误。

## 显式版本化数据库迁移

### 执行边界

- 新增只读命令 `mysql-schema-status`，报告当前版本、目标版本和待执行迁移。
- 新增显式命令 `mysql-migrate`，仅在用户主动调用时执行待处理迁移。
- 日常数据库命令只做版本预检。版本落后时停止并提示运行
  `mysql-migrate`，不得自动修改生产表。
- `mysql-init` 是显式建库命令，可创建当前基础表并登记基线版本。

### 迁移记录

新增 `schema_version` 表，字段至少包含：

```text
version
name
checksum
applied_at
```

- 迁移按固定宽度递增编号排序。
- 每个迁移具有稳定名称和内容校验值。
- 已执行迁移的校验值与仓库文件不一致时，状态检查和迁移均拒绝继续。
- 迁移在独立事务边界内执行并记录结果；失败不得登记版本。
- 现有 ERP 分摊补列逻辑迁入编号迁移，旧函数保留为兼容包装，但不再由普通导入隐式调用。

## 模块边界与兼容层

计划新增或抽取：

```text
src/work_order_process/
  import_failures.py
  api_transport.py
  schema_migrations.py
  ticket_import.py
  sync_log.py
  cli_commands/
```

职责如下：

- `import_failures.py`：失败类型、安全消息和有上限的失败收集器。
- `api_transport.py`：请求发送、瞬时状态判断和退避计算。
- `schema_migrations.py`：迁移发现、校验、状态报告和显式执行。
- `ticket_import.py`：工单月度/年度批次协调、详情拉取、提交与失败报告。
- `sync_log.py`：`sync_task_log` 的写入和只读查询。
- `cli_commands/`：按数据库、导入、导出和诊断域组织命令处理函数。

渐进拆分顺序为：

1. 先抽取无状态失败模型和 HTTP 传输。
2. 再抽取迁移和同步日志。
3. 再抽取工单批次导入。
4. 最后拆分 CLI 处理函数。

每次抽取后，旧模块必须重新导出原符号，现有测试继续从旧路径导入；新模块同时增加直接单元测试。不得在单一提交中搬移多个独立职责。

## CLI 修正

- `--customers-source` 的实际默认值和帮助文本统一为 `companies`。
- `--contacts-source` 的实际默认值和帮助文本统一为 `contacts`。
- `--personnel-file` 默认值改为 `None`。
- 执行 `mysql-import-personnel` 且未提供文件时，CLI 给出明确参数错误，不再隐式依赖带日期的本地文件名。
- 全部既有命令名称、参数名称和生产入口保持有效。

## 质量门禁

开发依赖增加 Ruff、pytest-cov 和 coverage。CI 及本地完整验证执行：

```powershell
uv lock --check
uv run --all-groups ruff check src tests
uv run --all-groups ruff format --check src tests
uv run --all-groups pytest --cov=work_order_process --cov-fail-under=70 -q
uv run --all-groups python -m compileall -q src tests
uv run work_order_process --help
uv run erp-merge --help
git diff --check
```

- 初始总覆盖率门槛固定为 70%，后续只允许提高。
- Ruff 格式化作为独立纯机械提交，避免与行为修改混合审查。
- CI 保留现有锁文件检查、仓库安全测试和完整测试。
- README、生产运维说明、项目接手手册及 AST/CLI 文档覆盖测试同步更新。

## 测试策略

### 客户台账

- 同日期重跑替换而非追加。
- 非法非空金额或日期使发布失败。
- 解析失败、临时表计数不符和正式表计数不符时旧快照不变。
- 业务清洗行与失败行分别计数。

### 失败模型

- 安全摘要包含阶段、记录标识或源行号及异常类型。
- 超过 100 条时报告总数、前 100 条和截断标记。
- 批量失败逐行回退后只记录最终失败行。
- 密码、电话、邮箱和完整载荷不会进入摘要。

### API

- 网络异常最多尝试三次。
- `429` 遵循 `Retry-After`。
- `502`、`503` 和 `504` 使用退避后重试。
- `401`、`403`、`404` 不重试。
- 现有客户端缓存、分页和 JSON 修复测试继续通过。

### 迁移

- 无版本表、已是最新、存在待迁移和校验值漂移状态。
- 迁移成功登记版本，失败不登记。
- 重复执行不重复变更结构。
- 普通数据库命令在版本落后时拒绝继续。

### 兼容性

- 原模块符号仍可导入。
- 全部 CLI 命令仍出现在帮助中。
- `daily_runner` 和 `erp-merge` 入口仍可执行帮助或导入检查。
- 动态交接手册测试覆盖新增模块、顶层符号和命令。

## 分阶段交付

1. 客户台账原子发布与严格解析。
2. 统一失败模型并接入台账、工单、客户和联系人同步。
3. HTTP 瞬时重试。
4. 显式版本化迁移及 CLI。
5. 同步日志、工单导入和 CLI 渐进拆分兼容层。
6. Ruff 格式化、质量门禁和文档更新。

每一阶段必须通过对应定向测试和当时的完整测试。最终交付时完整测试、覆盖率、Ruff、编译、锁文件、CLI 帮助、文档覆盖和差异检查全部通过，工作树仅保留用户原有未跟踪文件。
